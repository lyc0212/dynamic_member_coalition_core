## 4. 实施方案 C

### 4.1 增量资源计数

在 LocalJournal 内维护五类已成功持久化 STARTED 事件的增量计数：

- POLICY_WLS
- OBSERVATION_WLS
- SOLVER
- R
- ASSIGNMENT

初始计数全部为0。

只根据实际准备写入并成功提交的事件更新计数。

更新条件：

event_kind == RESOURCE_CALL

status == STARTED

属于对应资源类型。

计数更新必须位于真实持久化成功之后，即：

完整写入 → flush/fsync → 文件大小核对 → 增量哈希及提交状态更新。

持久化不确定时不得将本次记录计为成功提交，不得继续执行昂贵函数。

如果持久化成功之后的内部状态更新失败，必须进入既有失败停止路径，不得继续使用不可信计数。

RETURNED、FAILED、REJECTED 不重复计数。

保留底层 ResourceLedger 原有不可逆消费语义。不得将持久化计数失败解释为资源退款。

不将增量计数作为最终独立审计的唯一依据。

### 4.2 轻量计数接口

增加简单的增量计数查询接口。

日常资源查询和 reconcile 使用已成功提交的增量计数，不调用 LocalJournal.records()。

优先保留原 NestedJournal.committed_usage() 的磁盘独立读取语义，增加明确区分的轻量查询，避免已有审计代码被静默替换为缓存查询。

不额外维护完整历史 JSON 对象缓存。

不改变原 Journal 文件格式。

### 4.3 日常轻量检查

修改 Budget.check()、IndependentRecorder 日常对账及 initialized_budget 中的 integrity()。

正常资源调用检查继续保证：

- Budget/NestedJournal 状态合法。
- 非 POISONED、非 halted、非 invalid。
- 进程和线程身份一致。
- 文件身份与预期大小一致。
- 运行时资源计数与成功提交计数一致。
- 原存储预算满足。

移除上述日常检查中的完整 JSON 扫描及逐条摘要重算。

initialized_budget 中的 integrity() 直接复用 Budget.check()，不再独立重复扫描完整 Journal。

保留原 ResourceLedger、WLS 调用嵌套及预算限制。

### 4.4 原始字节哈希核验

保留现有累计 SHA256，不开发新的哈希机制。

增加简单的原始字节核验方法：

- 先执行文件身份和大小检查。
- 读取当前原始字节。
- 比较实际 SHA256 与已有增量 SHA256。
- 不解析 JSON，不逐条重新计算事件摘要。
- 发现不匹配则按现有完整性失败路径停止。

利用现有 ResourceLedger.outer 区分外层资源调用和嵌套 Solver 调用。

在外层 WLS、R 等自然完整性检查边界执行原始字节核验。

当 ledger.outer 已处于 WLS 调用内部时，嵌套 Solver 日常检查只执行轻量检查，不扫描完整历史字节。

保留最终完整磁盘审计。

本任务明确接受：同尺寸历史内容异常可能在下一原始字节核验边界或最终审计时才被发现，而非每个嵌套 Solver 调用前立即发现。

任何发现历史完整性异常的分支均不得通过最终接收。

不声称本地科研环境具备恶意并发篡改防御能力。

### 4.5 最终完整独立审计

不得删除或弱化 LocalJournal.records()、_records()、seal() 及 NestedJournal.audit() 的完整磁盘验证功能。

在 Budget.finalize() 内，从实际磁盘记录重新独立统计五类 STARTED 资源用量。

最终必须核对：

磁盘重新统计值 == 增量提交计数 == 权威运行时计数。

同时保留：

- 完整原始字节 SHA256。
- 完整事件摘要链。
- CALL_ID 及分配身份验证。
- CommitCredential 验证。
- 资源调用父子关系。
- STARTED 与终止事件闭合检查。
- R provenance 绑定。
- E0 写入冻结。
- seal、close 及不可逆最终化。

原有 WLS、R、Assignment 独立对账责任不得遗漏。

任一最终计数不一致或完整性验证失败，不能进入 FINALIZED_PASS。

不得通过缓存值替代最终磁盘独立验证。
